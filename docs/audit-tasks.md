## 1. Поиск кода, непокрытого юнит-тестами

## 2. Поиск кода, непокрытого интеграционными тестами

- [ ] Найти репозитории и HTTP-эндпоинты без интеграционных тестов на Testcontainers.

Проверять Doobie-реализации в `infrastructure/repository/` и route-хендлеры. Интеграционные тесты должны идти против реального PostgreSQL (Testcontainers), без моков БД. Цель — список репозиториев/эндпоинтов без интеграционного покрытия.

## 3. Поиск уязвимостей

- [ ] Найти нарушения безопасности.

Что искать: нарушения tenant-изоляции (фильтрация по `CompanyId` в каждом запросе, включая SQL-слой — `findById`/`delete`/`update`), утечки чувствительных данных в логах, SQL/CSV-инъекции, хардкод секретов, слабую обработку JWT. Цель — список уязвимостей с указанием места и серьёзности.

## 4. Поиск нарушений SOLID

- [ ] Найти нарушения принципов SOLID.

Что искать: бизнес-логику в route-хендлерах (должна быть в application-слое), перегруженные «god»-сервисы, нарушение разделения слоёв domain/application/infrastructure, неверные зависимости между слоями. Цель — список нарушений с указанием файла и принципа.

## Конкурентность: `markPayment` lost-update + регрессия CAS — 2026-06-22

> Контекст: статус-переходы поездки переведены на атомарный CAS (`updateIfStatus`) и смержены в master (`b0ca6c5`, запушено). При закрытии этой задачи всплыли две связанные проблемы вокруг `markPayment`. _Проверено лично по коду master._

- [x] **[HIGH] Регрессия: CAS-защита `markPayment` потеряна при merge** _(проверено лично)_ — ИСПРАВЛЕНО (agent/fix-markpayment-cas) — `ride/.../application/service/RideService.scala:635-662` — в master `markPayment` снова на безусловном `rideRepository.update(updatedRide)` без CAS. CAS-по-статусу для `Paid` (`updateIfStatus(_, Set(Completed))`), который был в коммите `9d405eb`, **затёрт версией master при merge `e966b8b`** (обе стороны меняли метод, авто-merge выбрал master-версию; тесты остались зелёными, т.к. concurrent-тест на этот путь не дошёл до master). Эффект: отменённая поездка снова может быть помечена `Paid` гонкой cancel↔markPayment. Нужно вернуть CAS-по-статусу. _Категория: Functional/Concurrency._
- [x] **[HIGH] Lost-update `markPayment` по payment-полям** _(проверено лично)_ — ИСПРАВЛЕНО (agent/fix-markpayment-cas) — `ride/.../application/service/RideService.scala:635-662` — read-modify-write: `getRideById` → правка `paymentStatus/paymentMethod/paidAt` в Scala → `update` без условия по полю. Два конкурентных `markPayment(Paid, Cash)` и `markPayment(Paid, Card)` на одной Completed-поездке перезаписывают друг друга (теряется метод/время платежа последнего проигравшего). CAS-по-статусу `{Completed}` это НЕ ловит — оба видят статус Completed. Денежный документ → требует атомарности. _Категория: Functional/Concurrency._

  **Варианты решения (выбрать при реализации):**
  1. **Field-level CAS для `Paid` (рекомендуется, соразмерно).** Новый метод репозитория по образцу `updateCheckpoint` (`PostgresRideRepository.scala:648-670`): `UPDATE rides SET payment_status='Paid', payment_method=?, paid_at=NOW() WHERE id=? AND status='Completed' AND payment_status<>'Paid'`, вернуть `affected_rows>0`. Условие `payment_status<>'Paid'` закрывает lost-update (второй конкурент видит `Paid` → 0 строк → already-paid, идемпотентно) И статус-гонку (`status='Completed'`) одним выстрелом. Pending/Unpaid оставить на обычном `update` (нет денежного риска). Без миграции. In-memory аналог — через `rides.modify` (как `updateIfStatus`).
  2. **Обобщённый `updatePaymentIfStatus(ride, expectedPaymentStatus, expectedRideStatus)`** для Paid/Pending/Unpaid. Полностью атомарно, но больше кода и открытый вопрос «что возвращать проигравшему не-Paid» (ошибка vs idempotent-noop).
  3. **Version-колонка `rides.version` + optimistic lock на все `update`.** Общее решение для всего репозитория, но требует миграции и затрагивает каждый вызов `update` — крупно и рискованно для узкой задачи; отклонено как несоразмерное.
